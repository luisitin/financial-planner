## The task

`qa/households/` holds 1,400 invented households (14 types × 100 variations). Alongside them, `lib/expect.mjs` holds the tester's own math for what each page should show, and `run.mjs` compares the app against it. Some cases fail.

**Step 1, the lead.** Read `lib/expect.mjs` and turn each figure it checks into a plain rule, with its formula, rounding and the page it belongs to. That rules sheet is every worker's brief. Then give each worker one type folder (`01-single-adult` ... `14-unusual-structures`); a big folder can go to two workers.

**Step 2, the workers.** Recompute by hand, from the case file and the rules sheet, every figure the case lists. Cover the base case, every case whose `INDEX.md` status is `fail`, and 10 random passing cases. Decide each disagreement:
- the app is wrong: a bug in the app;
- `expect.mjs` is wrong: a wrong expectation;
- the case asks for something the rules do not define: undefined.

Report one row per figure: `case_id, figure, app_value, expect_value, your_value, verdict, one-line reason`.

**Step 3, the lead.**
- Group the verdicts by root cause; one bug usually explains many cases.
- For each app bug, give a diff to the page's compute with a test.
- For each wrong expectation, give a diff to `lib/expect.mjs`.
- For each undefined case, write the decision into the case catalog.

Deliver the root-cause table first. The cases' `results/` folder is not in the repo, so reason from the case files and the code.

## How to answer

1. Start with a rationale of at most ten lines: what you changed and why.
2. Give a report in Markdown: findings ranked by impact, each with the file and line, why it matters and the fix. Then the changes for the top findings as unified diffs (or whole files for new ones).
3. A whole file goes in its own fenced code block whose first line is a comment with its path (`// path: modules/x/y/compute.js`).
4. End with the list of files you touched and the commands that verify them (`npm test`, `npm run check`).

Rules:
- Follow the project's rules in `AGENTS.md`: `compute.js` stays pure (no DOM, fetch, storage or timers); money math lives in code, never in an AI model; plain words on screen; every formula gets a test and a written source.
- Never edit `modules/registry.js` (generated by `npm run registry`), `data/` or `planner.properties`.
- Tests use `node:test` and `node:assert/strict`, in the module's `module.test.mjs` or `tests/<topic>.test.mjs`, so that `npm test` and `npm run check` stay green. Say which commands you ran; if you could not run them, say so plainly.
- Every number needs a source (IRS/SSA/CMS publication, statute, paper, or a worked example you show). Put the source next to the number in a comment and in the module README.
- The repo is public: use invented example data only (no real names, addresses, account numbers).
- If something is unclear, state your assumption and carry on; do not stop to ask.
- If you commit or open a pull request, put `Prompt: heavy-households-verify` on its own line in the commit message or pull request description.
